## 修改要求

### 第一阶段：完成 V0.2 发布

按以下顺序执行：

1. **提交整理后的文档及必要交付记录。** 确认新目录加入版本控制、被替代的旧 Markdown 删除；原始 JSON、XML、日志和题集保持可追溯。
2. **推送待发布分支并检查远程 CI。** 保存对应提交 SHA、运行链接及结果；若失败，定位并修复实际失败项。
3. **固定正式版本。** 在确认交付条件满足的准确提交上创建 `v0.2.0`，补齐正式发布说明及记录中的状态。远程发布明确对应同一提交。
4. **补充展示材料。** 按[演示指南](../../使用指南/演示指南.md)录制约五分钟：上传、重复跳过、完整回答、否定事实、无证据拒答、来源查看、重启恢复。展示资料使用现有公开样例。

本文件最初仅形成规划；以下“结果与证据”记录后来实际执行的发布步骤。

### 第二阶段：建议 V0.3 优先补齐文档管理

理由：当前用户可以上传、更新和提问，但缺少查看知识库内容及删除旧资料的操作。文档列表与删除能够完善日常使用流程，建议作为下一版本的小范围目标。

| 建议能力 | 修改要求 |
| --- | --- |
| 文档列表 | 从当前快照元数据展示文件名、文档标识、片段数量；说明应用保留 Chunk 和向量，不保存上传原文件 |
| 文档删除 | 通过文档标识删除对应文本、向量及稀疏检索内容；沿用快照事务，失败保留原 generation |
| 界面管理入口 | 支持查看已入库文档和确认删除，操作成功后更新列表及问答状态 |
| 重启与边界 | 删除结果重启后保持；删除最后一份文档、未知标识和保存失败均有清晰结果 |

确定进入 V0.3 时，另建 `版本记录/V0.3/001_版本规划.md`，定义接口、状态及验收用例；该阶段为建议，尚未开始实现。

### 第三阶段：用新增业务样本选择后续优化

在文档管理完成后，增加独立业务资料和未参与既有整改的新问题，沿用事实、数字、否定、引用及拒答门槛，同时记录延迟、内存和模型调用情况。保留现有 50 题作为历史基线，新结果使用新批次目录。

根据实际问题决定后续优先级：漏召回或排序问题对应检索/Reranker 对照；扫描资料需求对应 OCR；多人使用需求对应认证与知识库隔离。新增本地裁判模型继续按此前决定暂缓。
