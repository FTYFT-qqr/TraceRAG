# TraceRAG 版本规划 V0.1

## 1. 版本定位

TraceRAG V0.1 定义为：**最小可运行 RAG 闭环**。

本版本的目标不是追求功能丰富，而是稳定跑通以下核心链路：

> 导入文档 → 切分文本 → 建立索引 → 用户提问 → 检索证据 → 基于证据回答 → 返回引用 → 证据不足时拒答

只要这条链路稳定、可验证、可追溯，V0.1 即视为成功。

---

## 2. 功能范围

| 功能 | V0.1 要实现 | 暂时不做 |
| --- | --- | --- |
| 文档导入 | PDF、Markdown、TXT；同名文件更新时替换旧版内容 | Word、网页、OCR |
| 文档解析 | 提取正文，PDF 保留页码 | 复杂表格解析 |
| 文本清洗 | 去除明显空白和异常换行 | 高级语义清洗 |
| Chunk | 固定长度切分 + overlap | Semantic Chunking |
| 元数据 | 文件名、页码、`chunk_id`、`chunk_index` | 标签体系 |
| Embedding | OpenAI 兼容接口或配置的本地模型；校验模型与索引一致性 | 请求时动态选择模型 |
| 向量检索 | FAISS Top-K Search | BM25、Hybrid Search |
| RAG 回答 | LLM 仅依据检索内容回答 | Agent、联网搜索 |
| Citation | 返回来源文件、页码、Chunk；校验引用编号与拒答状态 | 自动化精细句级事实核验 |
| 拒答 | 简单相关度阈值 + Prompt 约束 | 学习型置信度模型 |
| API | `/health`、`/documents`、`/query` | 用户管理等非核心接口 |
| UI | Streamlit 简单问答界面，准确展示上传状态 | 正式 Web 前端 |
| 测试 | 核心模块基础 pytest 与真实问题的最小验收 | 完整评测体系 |
| 部署 | 本地运行 | Docker、Kubernetes、云部署 |

## 3. 最终用户体验

### 3.1 有足够证据时

```text
打开 TraceRAG
    ↓
上传 employee_handbook.pdf
    ↓
系统解析文档并建立索引
    ↓
用户提问：公司的年假有多少天？
    ↓
系统回答：正式员工每年享有 10 天带薪年假。[1]

来源：
[1] employee_handbook.pdf · 第 12 页
```

### 3.2 证据不足时

```text
用户提问：公司的股票期权什么时候可以行权？

系统回答：根据当前知识库，我无法确认这个问题。
```

## 4. 开发阶段

V0.1 分为 8 个阶段，按顺序开发和验收，不同时铺开。

### 阶段 1：项目骨架

**目标：** 建立 `app/`、`tests/`、`data/`、配置文件和 FastAPI 入口。

**重点：** 先形成结构简单、能够运行的项目基础，不提前引入后续功能。

**验收标准：** 项目可以正常启动，`GET /health` 返回健康状态。

### 阶段 2：Document Loader

**目标：** 实现 PDF、Markdown、TXT 读取，并统一转换为内部数据结构。

**重点：** PDF 必须保留页码；所有文档必须保留文件名和来源信息。

**验收标准：** 可以输出每页或每段的文本、文件名和页码。

### 阶段 3：Chunk Pipeline

**目标：** 实现文本清洗、固定长度切块、overlap，并生成稳定的 `chunk_id`。

**重点：** 每个 Chunk 至少保存 `content`、`document_id`、`file_name`、`page_number` 和 `chunk_index`。

**验收标准：** 随机抽取任意 Chunk，均能追溯到原始文档及对应页码。

### 阶段 4：Embedding + FAISS

**目标：** 使用配置的 OpenAI 兼容接口或本地 Embedding 模型，将 Chunks 向量化并建立 FAISS 索引。

**重点：** 索引与 Chunk 元数据的映射必须稳定，并支持持久化。

**验收标准：** 程序重启后可以加载已有索引，无需重复执行 Embedding；模型与索引不一致时按整改编号 7.3 明确拒绝混用，详见 [基础整改记录 001](../../整理记录/版本0.1/整改记录/01_基础整改.md)。

### 阶段 5：Vector Retriever

**目标：** 实现统一的向量检索接口，例如 `retrieve(query, top_k=5)`。

**重点：** 返回 Chunk、元数据和相关度分数；本阶段不接入 LLM。

**验收标准：** 使用真实文档、实际 Embedding 模型和十几个问题验证，正确证据大多数能够进入 Top-K；具体记录与门槛见 [基础整改记录 001](../../整理记录/版本0.1/整改记录/01_基础整改.md) 的整改编号 7.4。

### 阶段 6：RAG + Citation + Reject

**目标：** 将 Top-K Context 提供给 LLM，生成仅基于证据的回答，并实现引用和拒答。

**重点：** Citation 应对应实际使用的证据；当 Top-1 或 Top-K 相关度过低时拒答。

**验收标准：** 以下三种情况均通过：

- 有答案的问题能够正确回答；
- 回答附带可追溯来源；
- 没有足够证据的问题不会编造答案。

当前引用和拒答的补充要求见 [整改规划 003](../../整理记录/版本0.1/整改记录/03_拒答评分与参考范围.md)。

### 阶段 7：FastAPI + Streamlit

**目标：** 将已完成的 RAG Pipeline 封装为 API 和简单界面。

**重点：** API 仅保留 `GET /health`、`POST /documents`、`POST /query` 三个核心接口；Streamlit 仅负责文件上传、问题输入，以及回答、引用和调试检索结果的展示。

**验收标准：** 用户能够在浏览器中完成“上传文档 → 提问 → 查看回答与引用”的完整流程；首次、重复和更新上传的提示符合 [基础整改记录 001](../../整理记录/版本0.1/整改记录/01_基础整改.md) 的整改编号 7.5。

### 阶段 8：基础测试与 README

**目标：** 为核心流程补充基础自动化测试和项目说明。

**重点：** 测试至少覆盖 Chunk、Retrieval 和 API 基本流程；README 说明启动方法、项目架构、支持能力与当前限制。

**验收标准：** 核心测试可以稳定通过，同名更新与模型切换等回归场景得到覆盖，新使用者能够按照 README 在本地启动项目。

## 5. 核心数据结构

V0.1 围绕以下四个结构设计，不提前建立大量 DTO。

### Chunk

```python
class Chunk:
    chunk_id: str
    document_id: str
    content: str
    file_name: str
    page_number: int | None
    chunk_index: int
```

### RetrievalResult

```python
class RetrievalResult:
    chunk: Chunk
    score: float
```

### QueryResponse

```python
class QueryResponse:
    answer: str
    rejected: bool
    citations: list[Citation]
```

### Citation

```python
class Citation:
    chunk_id: str
    file_name: str
    page_number: int | None
    text: str
```

## 6. V0.1 明确不做

以下内容不属于 V0.1 范围：

- BM25、Hybrid Search、Reranker
- 完整 Evaluation Framework
- SQLite、SQLAlchemy
- 用户系统、登录注册、权限、知识库空间、多租户
- Celery、Redis、消息队列
- LangGraph、Agent、GraphRAG、知识图谱
- OCR、复杂表格、图片理解
- React、Vue
- Docker、Kubernetes、云部署

其中 BM25、完整 Evaluation Framework 和 Bad Case Analysis 计划放入 V0.2。推荐的后续迭代路径为：

```text
V0.1 Vector Baseline
    ↓
扩展并规范 Evaluation Dataset
    ↓
发现并分析 Bad Case
    ↓
加入 BM25 + RRF
    ↓
重新评测
    ↓
验证 Recall@K 是否提升
```

## 9. 开发与文档原则

采用逐阶段开发和验收方式：**前一阶段验收通过后，再进入下一阶段。**

- 每轮复核发现需要修改的事项，自动新建对应版本目录下的独立编号 Markdown；记录现状、修改要求、验收方式和状态。
- 编号在每个版本内递增，文件名采用“三位编号_主题.md”，例如“004_主题.md”；同一天的不同轮次也分别编号。
- 同一轮规划的实施进展和验收结果更新到该轮文件；新的复核轮次另建文件。
- 本版本总览只更新简要状态和文档链接，不追加详细问题、实施日志或整段历史报告。
- 更新 [文档索引](../../文档导航.md)，保留旧记录与原问题编号，方便回溯。
- 验收报告保留测试及实际回答等证据；规划引用报告，避免重复复制。
- 此规则替代此前“每次把所有问题追加到同一版本规划”的记录方式。

V0.1 满足全部整改和冻结标准后，下一版本再集中解决完整评测、Bad Case 分析和混合检索优化。
